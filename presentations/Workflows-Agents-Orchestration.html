Act 1 · Workflows · daily rhythm One session per phase · /clear between

Fresh context,
every phase.

How developers actually run Claude Code day-to-day. Open a session to plan. /clear or a new terminal to review the plan. Another to implement. Another to review the diff. Each phase gets a clean mind with no stake in the prior one — the writer / reviewer split made real, by hand. Slide 13's orchestrator FSM automates this exact loop.

The day-to-day · one session per phase
same terminal · four contexts · /clear between
# Session 01 · plan claude "/plan OAuth refresh-token rotation" plan.md written · session auto-named # Session 02 · review plan (fresh context) claude --permission-mode plan "Review @plan.md." APPROVED # Session 03 · implement claude "Implement @plan.md in a worktree." # Session 04 · review diff (fresh context again) claude -p "Review diff vs @plan.md." MUST_FIX · 2 findings
Why fresh context
A Claude that just wrote the code will defend it. A Claude that only reads the diff will not. /clear (or a second terminal) wipes that bias — the reviewer's only input is the artifact on disk.
Cap revise loops at 3 iterations; escalate to a human after that. Infinite revision is a failure mode, not progress.
Primitives at hand
/planPlan mode — read-only.
/clearHard reset between phases.
/resumeRestore a prior session.
/rewindJump back to a checkpoint.
2nd terminalParallel reviewer, same repo.

Act 1 · Workflows · the toolbox Six primitives · one reference card

Pick the
right primitive.

The loop is the recipe; these are the ingredients. Every Claude Code customization slots into one of six primitives — pick the right one or fight the system. The Gotcha column is where most engineers burn time.

Primitive Lives in When to use Gotcha
CLAUDE.md ~/.claude/ · ./ · parents Always-on rules & conventions Bloat kills adherence — keep < 200 lines
Skills .claude/skills/<n>/SKILL.md Reusable knowledge + multi-step workflows Body stays in context once invoked — keep < 500 lines
Hooks settings.json · hooks{} Must happen every time, no judgment Runs with full perms · deny beats bypassPermissions
MCPs .mcp.json (project · committed) External systems · Jira · Sentry · DB · GH Approval prompted first run · prefer HTTP over SSE
Subagents .claude/agents/*.md Investigation / verification protecting main context Cannot nest — no subagent spawns subagent
Settings settings.json (5 scopes) Permissions · hooks · env · MCP toggles Rules merge: deny → ask → allow · no secrets
Heuristic
CLAUDE.md is advice the model may follow. Hooks are guarantees. Skills are reusable workflows. MCP is plumbing. Don't mix them.
Setup ladder
Wrong twice → CLAUDE.md · repeated → Skill · external data → MCP · must-happen → Hook · second repo → plugin.

Act 1 · Workflows · enforcement Hooks · deterministic enforcement

Guardrails,
not advice.

"Never edit .env" in CLAUDE.md is a request the model may honour. A PreToolUse deny is enforcement — and beats even bypassPermissions.

Event roster · high leverage
PreToolUse · PostToolUsearound tool calls
UserPromptSubmit · Stoparound the turn
SessionStart · SessionEndinit / cleanup
SubagentStop · PreCompactsubagent + memory
Exit-code semantics
0proceed · stdout becomes context for UserPromptSubmit / SessionStart
2block · stderr fed back to Claude as feedback
othernon-blocking error · logged but ignored

Hook types: command · http · mcp_tool · prompt (LLM-judged) · agent (multi-turn LLM with tools).

.claude/settings.json — two safety nets
{ "hooks": { "PostToolUse": [{ "matcher": "Edit|Write", "hooks": [{ "type": "command", "command": "prettier --write $FILE" }] }], "Stop": [{ "hooks": [{ "type": "prompt", "prompt": "All tests pass?" }] }] } }
Cheap TDD safety net
A PostToolUse formatter plus a Stop prompt-hook asking "all tests pass?" make shipping broken code structurally difficult, not just frowned upon.

Act 1 · Workflows · reuse Skills & slash commands

Description
is destiny.

When the loop becomes muscle memory, freeze it into a Skill. Skills and slash commands share one invocation system — Skills are the strict superset. Write Skills for everything new.

Same system · same file format
.claude/skills/deploy/SKILL.mdcreates /deploy
Skills add
  • Supporting files in the skill directory
  • YAML frontmatter (allowed-tools, argument-hint)
  • Auto-trigger by description — cap 1,536 chars
  • disable-model-invocation: true for side-effecting commands
  • $ARGUMENTS, $0..$N, !cmd for shell at expand time
Precedence
enterprise > personal > project. Plugin skills namespaced plugin:skill.
.claude/skills/ship-feature/SKILL.md
--- name: ship-feature description: spec → plan → tests → impl → review → commit → PR disable-model-invocation: true allowed-tools: Bash(gh *) Bash(git *) Bash(npm test*) argument-hint: [feature-name] --- Ship $ARGUMENTS end-to-end: 1. Read SPEC.md ($ARGUMENTS section). 2. Enter plan mode. Produce PLAN.md. 3. Write failing tests first (red). Confirm fail. 4. Implement until tests pass (green). Refactor. 5. Spawn subagent: "Review @PLAN.md vs diff". 6. Commit with message. gh pr create.
Description trap
If your description matches your internal vocabulary instead of how teammates phrase requests, the auto-trigger will never fire — and you've just built a slash command with extra steps.

Act 2 · Subagents · the mental model Workflow · Agent · Team

Start small.
Escalate only when forced.

Before we add a second mind to the picture — Workflow, Agent, and Team are nested scopes of coordination. Always start at the smallest one that solves the problem. Don't reach for a team when a workflow inside one agent is enough. Act 2 is what happens when one workflow isn't.

01 · Workflow
An agentic loop too big for one context.
Plan → review → implement → review → commit, with revise loops verifying each step. More than one agent can hold in a single session — so each step runs as a fresh agent.
02 · Subagents
Main agent fans out.
The main agent spawns subagents in isolated fresh contexts. Each does its work and reports a summary back. One level deep — no nesting.
03 · Agent Teams
Lead + shared list.
Team lead spawns teammates and seeds a shared task list. Teammates claim tasks and chat peer-to-peer via SendMessage. Needs EXPERIMENTAL_AGENT_TEAMS=1.

Act 2 · Subagents · the primitive Fresh mind · isolated context

An agent is a
fresh mind.

When one context can't hold the problem, fan out. A subagent is a context-isolation primitive — its own window, system prompt, tool allowlist. Parent sees the final text only; intermediate tool calls stay isolated.

Hard rule · no nesting
Subagents cannot spawn subagents. One level deep, always. Chain from the parent, or extract a Skill.
Token laundering
A subagent burns 50k tokens reading 40 files, hands back a 400-token summary. Parent context stays clean.
main agent · one Scout subagent · token laundering in practice
> Map every call site of useAuth() in src/ and summarize. * Contemplating… (esc to interrupt) • I'll dispatch a Scout subagent — fresh context, read-only tools — so my window stays clean. • Explore(Map useAuth() call sites) └ Done (40 tool uses · 52.3k tokens · 31s) * Clauding… (esc to interrupt) • useAuth() — call-site map Called from 40 sites across 23 files, concentrated in components/ (28) and hooks/ (9). Three call sites destructure { token } directly — these will break when rotation lands. Refactor those three to getToken() before shipping the change.
Model tier · May 2026
Opus 4.7Best for debugging and the initial plan / architecture — hard reasoning, ambiguous specs.
Sonnet 4.6Best for executing the plan / implementation — the ~80% workhorse.
Haiku 4.5Best for parallel scouts, fan-out, and cheap classification.

Dispatch patterns — when to fan out
Scout
Many read-only Explore agents in one message — map a codebase fast.
Specialist
One agent per domain (auth, DB, UI) — each stays expert.
Pipeline
Chain A → B → C when each step needs the prior step's output.
Worktree
Isolated git worktrees — edits never collide; auto-cleaned.
Background
Long jobs (tests, builds) run async while you keep working.
Fan-out
Opus plans → cheap Haiku workers in parallel → Sonnet merges.
.claude/agents/code-reviewer.md
--- name: code-reviewer description: Senior reviewer. MUST be used immediately after an implementation agent reports done tools: Read, Grep, Glob, Bash(git diff:*), Bash(npm test:*) disallowedTools: Edit model: sonnet effort: high isolation: worktree color: red --- You are a staff engineer. Run git diff --stat first, then deep-read changed files. Output: CRITICAL / WARNING / SUGGESTION End with APPROVED or BLOCKED.
"Never delegate understanding"
If the parent can't define success in one sentence, three parallel subagents will return three flavors of confusion at higher token cost.

Act 2 · Subagents · cost discipline Model selection · resolution order

Match the model
to the task shape.

Haiku scouts, Sonnet implements, Opus reasons. Never pay Opus prices for a Haiku-shaped task — but never starve a debugging agent of Opus to save $0.40.

Tier guide
ModelUse forCost
Haiku 4.5 Parallel scouts · greps · file lookups · dispatched in bulk Cheap · fast
Sonnet 4.6 Default — most subagents, most implementation, ~80% of work Balanced
Opus 4.7 Hard reasoning · architecture · hairy debugging · ambiguous specs Expensive
Resolution order · first wins
CLAUDE_CODE_SUBAGENT_MODEL → per-invocation → frontmatter model: → parent session

Caveat: the env var doesn't override built-ins that hardcode their model (Explore stays Haiku).

Effort field · thinking models only
low medium high max

max ≈ 3–5× latency for marginal quality on routine tasks. Reserve for adversarial reviews + gnarly debugging.

Canonical fan-out
Opus orchestrator (effort: high)
↓ decomposes
3–5× Haiku scouts (parallel)
↓ consolidates
1× Sonnet implementer
↓ verifies
1× Sonnet reviewer (effort: high)
cost-capped CI run
# force every custom subagent to Haiku CLAUDE_CODE_SUBAGENT_MODEL=haiku claude -p \ "/audit-deps and report" # built-ins keep their hardcoded models
Pin model IDs in plugins
sonnet resolves to whatever is current — breaks reproducibility across version bumps. Pin full IDs (e.g. claude-sonnet-4-6) in plugin agents.

Act 3 · Orchestration · the pattern From recipe to system

From recipe
to orchestrator.

The canonical loop — Plan → Review → Code → Review — re-implemented as a finite-state machine. Each step is a fresh subagent; files on disk are the medium between them. The parent Claude is the lead — there is no team, just a state machine and four specialists.

The shape · finite-state machine
01 · The shape
A finite-state machine mirroring the canonical loop. Five states, four edges forward, two edges back. The lead Claude is the state machine — it picks the next state from the last file written.
plan
→ plan-review
→ implement
→ impl-review
→ done
02 · The workers
Four specialized subagents, each spawned fresh per visit. Own context. Own model. No nesting — the lead is the only orchestrator.
planner · Opus · high
plan-reviewer · Sonnet · read-only
implementer · Sonnet · worktree
impl-reviewer · Sonnet · runs tests
03 · The medium
Files on disk are the contract between subagents. Files survive crashes, resumes, and context resets — messages do not. Each artifact is durable truth and a state transition.
plan.md · planner writes
plan-review.md · reviewer writes
impl-notes.md · implementer writes
impl-review.md · reviewer writes
Why it works · iron disciplines
· Plan-then-code, never the other way — a written plan is the precondition for any edit.
· The reviewer always reads the diff — never the agent that wrote it. Fresh context kills the defend-your-own-code bias.
· Loops cap at 3 iterations, then escalate to a human. Infinite revision is a failure mode, not progress.
· APPROVED / findings is the wire format — a machine-checkable contract, no LLM judge required.

Practices · two iron laws Two iron laws · one discipline

Two iron laws.
One discipline.

TDD iron law
No production code without a failing test first. Watch each test fail before implementing. RED → GREEN → REFACTOR.
Verification iron law
No completion claim without fresh verification evidence in the same message. Banned without evidence: "should pass", "looks good", "Perfect!".
Setup ladder · grow over time
wrong twice→ CLAUDE.md→ Skill→ MCP→ Hook→ Plugin

Encode every recurring correction. Every time you type the same fix, that's a missing primitive somewhere.

Permission modes · quick ref
default acceptEdits plan auto dontAsk bypassPermissions

Precedence high → low: managed > CLI > local > project > user. Merge: deny > ask > allow.

Do

  • Commit .claude/ — settings, skills, agents, commands, rules.
  • Give Claude a way to verify — tests, lints, screenshots, type-check.
  • Plan-first for non-trivial work · set "defaultMode": "plan".
  • Prune CLAUDE.md < 200 lines · scope rules via paths:.
  • Subagents for context-heavy work · let Haiku scouts burn the tokens.
  • Write Skills, not slash commands, for new work.
  • Prefer CLIs (gh, aws, gcloud) over raw APIs.

Don't

  • Bloat CLAUDE.md — Claude re-asks what's buried inside.
  • Rely on prose for guardrails — use hooks for must-happen.
  • Ship a single mega-agent doing plan + code + review in one context.
  • Write Skill descriptions in internal jargon — match user phrasing.
  • Commit secrets in settings.json / .mcp.json.
  • Run infinite-exploration sessions with no scope · cap loops at 3.
  • Nest subagents — they cannot spawn other subagents.

Practices · cheat sheet The ten · one page

Ten rules,
one page.

1
Right primitive
Re-explain → CLAUDE.md; multi-step → Skill; must happen → Hook; external data → MCP.
2
Description is destiny
For Skills (≤ 1,536 chars). Body sees $ARGUMENTS; Skill wins on /name collision.
3
Hooks always fire
Exit 2 blocks; exit 1 does not. PreToolUse deny beats bypassPermissions.
4
Keep CLAUDE.md lean
CLAUDE.md < 200 lines. CLAUDE.local.md is deprecated — use @imports.
5
Plan mode first
For anything non-trivial. /plan · Shift+Tab · Ctrl+G to edit before approval.
6
Subagents don't nest
Isolated, return one summary, cannot spawn subagents (one level deep, always).
7
Verify everything
"Never delegate understanding." Trust-but-verify every agent report — always git diff and run tests.
8
Parallel dispatch
N Agent calls in one assistant message run concurrently — independence required.
9
Orchestrator pattern
A lead Claude runs a state machine, dispatches specialized subagents per gate, caps loops at 3, escalates to human.
10
Model tier
(May 2026): Haiku 4.5 scouts · Sonnet 4.6 general · Opus 4.7 synthesis. Pin IDs in plugins.
Remember
Loop first. Verify with evidence.
Start small. Escalate only when forced.

End
Closing thoughts

Build
over time.

The strongest Claude Code setups in the wild aren't the most elaborate — they're the most lived-in. Start with CLAUDE.md and the canonical workflow. Add Skills when you repeat yourself. Add Hooks when prose stops being enough. Add subagents when context blows up. Reach for orchestration only when one Claude can't carry the loop.

Each layer earns its place. Don't ship the whole pyramid on day one. Encode your team's actual habits, not aspirational ones.
